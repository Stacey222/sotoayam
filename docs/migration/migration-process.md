## Forward-only rules

1. Never edit a migration once it may have been applied.
2. Use UTC sortable filenames: `YYYYMMDDHHMM_description.sql`.
3. One migration has one bounded purpose; schema and risky backfill should be separate when practical.
4. Every migration is reviewed for locks, defaults, backfill volume, RLS, indexes, foreign keys, and rollback boundary.
5. RLS is enabled for new protected tables before exposure; no public write policy is created for convenience.
6. Service-role credentials remain server-side.
7. Destructive migrations require separate explicit approval, verified backup/restore, and completion of the compatibility window.

## Additive migration sequence

```text
add nullable/additive structure
-> deploy compatible code
-> idempotent backfill
-> reconcile old/new
-> switch reads behind a flag
-> observe
-> stop legacy writes
-> enforce stronger constraints
-> deprecate only with separate approval
```

Do not add a `NOT NULL` constraint or foreign key until existing rows are validated/backfilled. Avoid table-wide default rewrites and long locks; test query plans and lock behavior against representative volume.

## Review evidence required per migration

- New migration filename and checksum.
- Intended live migration predecessor.
- DDL/backfill scope and estimated affected row count.
- Application version/feature flag that consumes it.
- Compatibility effect on `/start`, Admin API/UI, notification endpoint, and diagnostics.
- Automated migration/contract tests.
- Pre/post safe schema check.
- Rollback action and owner.
- Audit of RLS/policies and secret handling.

## Backfill rules

- Idempotent and resumable; use stable unique keys/bridge columns.
- Report aggregate counts only, not Telegram identifiers or names.
- Unknown Divisi/Role values go to remediation, never guessed mapping.
- Preserve legacy Role values without granting permissions.
- Run in bounded batches when volume warrants it.
- Reconciliation must be zero-mismatch before authoritative read cutover.

## Rollback principles

Slice 0 source rollback is the local baseline Git commit. Current runtime rollback is the `telegram_users` implementation represented by that commit.

For future additive migrations, rollback normally means:

1. disable the new feature/code path;
2. return reads and writes to the verified legacy path;
3. leave additive tables intact for diagnosis;
4. repair/reconcile forward;
5. do not automatically drop schema or erase migrated data.

Database-destructive rollback SQL is not generated by default. Restoration from backup is an incident procedure, not a routine migration reversal.

## Compatibility window

A legacy field/table may be deprecated only after:

- all consumers are inventoried and migrated;
- comparison metrics show zero unexplained mismatch for an approved observation period;
- rollback to legacy has been tested;
- current contracts have a versioned replacement;
- IT approves cutover;
- destructive removal receives separate approval.

## Deployment checklist

Before:

- clean source-control state and recorded baseline SHA;
- `npm run check:migration-baseline` passes;
- approved backup/restore point where appropriate;
- live migration registry checked through authorized tooling.

After:

- apply only the intended forward migration;
- run safe schema/contract checks;
- verify `/start` and affected API behavior proportionally;
- reconcile aggregate counts;
- record migration version/checksum and outcome;
- retain rollback flag through the compatibility window.
